# 63차 즉흥 행동의 성공 계약 제안

2026-11-09. 자문 전용. 이 문서만 작성했다. 소스·콘텐츠·시험을 수정하거나 서버·실제 GM·시험·커밋·CodeRabbit을 실행하지 않았다. `gm.ts`와 `prompt.ts`는 문법 담당 작업자의 소유이므로 아래 내용은 인계할 계약이다.

## 결정

**기법과 성공 목표를 분리한다.** 해석기는 이번 행동의 기법·능력치·난도와 목표를 정하고, 엔진은 작가가 정의한 목표의 효과·도착지를 적용한다. hit와 mixed는 같은 목표를 달성한다. mixed만 목표와 양립하는 별도 비용을 낸다.

기존 접근법에는 이미 도주·관찰·정보 은폐 등의 성공 효과와 경로가 있다. 이를 새로 추론하거나 모델에게 쓰게 하지 않고 작은 `GoalSpec`으로 뽑아 공유한다. 즉흥 행동을 기존 접근법 자체로 바꾸지는 않는다. 가령 모래를 뿌려 도망치기는 도주 목표를 쓰되, 가방으로 칼을 밀었다는 고정 동작·소지품 조건·능력치를 가져오지 않는다.

관련 없는 현실 행동도 받는다. 입 맞추기처럼 **그 자리에서 완료되고 후속 대본의 지속 상태를 바꾸지 않는 목표**는 `local`로 판정한다. 성공한 사건은 판정 기록에 남긴다. 도주·무장 해제·물건 소유·지속적인 부상처럼 이후 상태나 경로를 바꾸는 목표를 `local`로 숨기지 않는다.

물리적으로 불가능한 목표, 또는 가능하지만 현재 콘텐츠에 후속 상태가 구현되지 않은 목표는 **굴리기 전에** 범위를 밝힌다. 실행 가능한 대안을 명시한 확인 카드에서 동의한 경우에만 그 대안으로 판정한다. 둘은 다른 이유다. “후속 경로 미구현”을 “아시나는 할 수 없다”로 포장하지 않는다. 기존 목표로 좁힐 수 있다는 이유만으로 자동 축소하지 않는다.

이 제안은 임의의 **기법**과 현장 사건을 수용하는 최소 계약이다. 모든 임의의 지속 세계 상태와 이후 이야기를 생성하는 샌드박스까지 제공한다는 뜻은 아니다. 그 요구에는 별도 세계 상태·후속 장면 모델이 필요하며, 문자열 하나와 기존 대본으로 구현했다고 주장할 수 없다.

## 최소 데이터 변경

### 1. 작가가 소유하는 성공 목표

`app/src/engine/types.ts`에 다음 구조를 둔다. 아래는 구현 계약을 설명하는 타입이며 실행 코드를 추가한 것이 아니다.

```ts
interface GoalSpec {
  text: string;       // 이번 판정에서 확정할 정확한 성취와 범위
  effects?: Effects; // 성공 자체의 상태. 기법 전제나 비용을 넣지 않는다.
  next: Next;        // 성취를 보존하는 후속 비트. 모델이 쓰지 않는다.
  price: string[];   // mixed에 허용한 독립 비용 ID
  if?: string;      // 현재 상태에서 이 목표를 약속할 수 있는 조건
}

// 추가 필드
// FreeSpec.goals?: Record<string, GoalSpec>
// ApproachSpec.goal?: string
// ImprovMark.target?: string  // 목표 ID 또는 예약값 "local"
// LogEntry(kind: "check").improv?: ImprovMark
```

- 새로 굴리는 현실 즉흥 행동은 `target`과 안전한 `deed`가 반드시 있다. 선택 필드는 옛 저장·비판정 absurd/odd 자료를 읽기 위한 호환 경계이며 새 판정의 생략 허가가 아니다.
- `deed`를 새 성공 문자열과 중복하지 않는다. 의미를 “이 입력의 **성공 시 확정할 사건**을 과거형으로 요약한 문장”으로 정한다. 판정 전에는 계획이고, miss에서는 이뤄진 사실이 아니다. 단순 동작뿐 아니라 입력한 목적까지 보존한다. `(모래를 뿌려 달아난다)`를 “모래를 집었다”로 요약하면 파싱 실패다.
- goal ID는 장면 안에서 유일하며 기존 접근법 ID를 되도록 재사용한다. `local`은 예약값이다. 목표 표는 버튼 목록과 별개라서 새로운 목표를 추가해도 선택지 단추를 강제로 늘리지 않는다.
- `next`는 생략하지 않는다. 기존 goal 효과와 기존 beat.next를 확인해 같은 경로를 명시적으로 옮긴다. 조건부 Next는 성공 효과 적용 상태에서 선택하고, 비용 전에 실제 도착 비트 ID로 고정한다.
- `ApproachSpec.goal`이 있으면 고정 접근법에도 같은 성취를 적용한다. 기존 hit/mixed에서 그 성취 효과를 **이동**하고 중복 적용하지 않는다. 기법 때문에 판정 전에 실제로 일어나는 before는 그대로 둔다. “쓸모를 증명했다”처럼 성공해야 하는 표시는 before에서 목표 효과로 옮긴다.
- 성공 목표와 관계없는 보너스·실패 효과·연출은 기존 outcomes에 남긴다. 목표가 있는 hit/mixed/crit의 outcomes는 목표를 뒤집는 flags/lose/next를 갖지 못한다. next의 소유자는 GoalSpec 하나다.
- 목표를 처음 추출할 대상: b02의 접근·관찰·회피, b05의 협상·신분·도주·정확한 물건 제시, b06의 회피·방어·도주, b08의 시선 유지·귀찌 은폐, r3의 물/쉼터/방향, r4/r5의 증명. 같은 goal을 쓰지 못하는 입력을 이름이 비슷하다는 이유로 연결하지 않는다.
- b08/r2/r4/r5에서 도주가 실제로 가능하도록 받으려면 그 free에도 도주 목표와 `r3_flee` 등 **현재 위치에 맞는 경로**를 등록한다. 도주 목표 없이 local로 처리하지 않는다. 경로에 이미 포박·물품 압수가 있었다면 되돌리는 효과도 명시한다. 다른 비트의 목표를 런타임에 검색해 빌리지 않는다.

`GoalSpec.price`는 새 목표의 비용 소유권을 정하기 위한 목록이다. 기존의 목표 없는 결과는 `Outcome.price`를 유지한다. 인라인 비용과 `price: []`인 리드 WIP도 유효하다. 목표를 추출할 때는 해당 인라인 비용을 목표의 허용 PriceSpec으로 옮기고 한 번만 적용한다. 기존 전체 콘텐츠를 같은 순간 무조건 재작성할 필요는 없지만, 목표로 내보내는 항목에는 한 소유자 규칙을 지켜야 한다.

### 2. 모델 출력과 내부 해석

기존 평평한 `interpretSchema`에 **두 필드만** 추가한다.

| 필드 | JSON 범위 | 의미 |
|---|---|---|
| `target` | 현재 허용된 `free.goals` ID, `local`, `none` | 성공 상태의 참조. 기법을 고르는 기존 approach와 별개다. |
| `scope` | `ready`, `clarify`, `none` | 즉시 처리 가능한 목표인지, 승인받을 범위 조정인지, 비판정 입력인지 |

기존 `reason`은 범위 조정 이유에도 사용한다. 길이 제한은 40자에서 160자로 늘리고, 화면용 기존 label만 현재처럼 줄인다. `deed`의 60자 한도 안에 목표 전체를 적을 수 없으면 여러 목표를 몰래 버리지 않고 clarify로 보낸다.

경계 파싱 규칙:

1. `ready + target ID`: 목표의 조건이 맞고 입력의 성공 목적과 정확히 같은 경우만 허용한다. 새로운 기법이면 기존 approach로 되돌리지 않고 improv를 유지한다.
2. `ready + local`: 요청한 성취가 그 자리의 완료 사건이고, 이어질 대본이 그 사실을 취소하거나 미완료 지속 상태를 가정하지 않을 때만 허용한다.
3. `clarify + target ID/local`: `reason`은 원래 목표와 제안 범위의 차이·이유, `deed`는 승인할 대안의 성취다. 내부 `Interpretation`에 `kind: "clarify"`, `message`, `proposal`을 추가한다. proposal은 원래의 stat/difficulty/bold/deed/target/risk/source를 가진 실행 가능한 즉흥 계획이다.
4. `clarify + none`: 실행 가능한 대안이 없는 경우다. 내부 clarify에 proposal을 넣지 않는다. 짧은 직접 재입력 안내와 기존 선택 수단을 유지하며 굴리지 않는다.
5. `none + none`: ask/talk/idle/absurd/판정 없는 odd. 기존 처리로 간다. `absurd=true`를 target보다 먼저 분기한다.
6. ID 불일치, 빈 deed, ready+none, 현재 조건에 맞지 않는 목표는 경계 오류다. 기존 byRule이 목표 없는 즉흥 판정을 만들어 대신 굴려서는 안 된다. 비판정 입력의 기존 복구는 유지하고, 해석에 실패한 실제 행동은 무소비 rewrite로 돌려보낸다.

모델에 주는 목표 목록은 `id + text + 지금 성립하는 조건`이다. 효과·행선지·미공개 미래 장면을 플레이어에게 노출하지 않는다. 모델이 효과, flag 이름, price ID, next를 만들도록 스키마에 열어 두지 않는다. goal text와 deed의 의미 일치는 모델 해석의 책임이며 실제 모델 사례로 검증한다. 문자열 열거로 증명됐다고 말하지 않는다.

기존 `approach`는 고정 기법까지 맞을 때 쓴다. `target`만 같고 기법이 다르면 improv다. 소지품 규칙의 빠른 반환과 `byRule`도 이 경계를 따라야 한다. 물건 이름만 맞는다는 이유로 지도 꺼내기 같은 고정 성취를 확정하지 않는다.

### 3. 확인과 저장

`pendingIntent`와 기존 `confirm kind: intent` UI를 재사용한다. pending에 `target`, 원래 `bold`, 범위 안내용 `message?`를 더하고 기존 text/deed/stat/difficulty/source/risk 관련 정보를 보존한다. 확인 후 bold를 무조건 true로 만드는 현재 복원을 없앤다.

- 범위를 줄이는 경우: “원래 목표를 지금 약속할 수 없는 이유. 이번 판정에서는 무엇까지 가능한지. 이 범위로 시도할지”를 한 카드에서 묻는다. yes는 승인한 계획, no는 비용 없는 취소다. 다른 글은 기존 dropIntent 뒤 새 입력으로 받는다.
- scope 확인은 `guardRisk`, `noteSaid`, `noteHeard`, identity 효과, interject의 pending 줄 삭제보다 먼저 한다. 승인하지 않은 행동·대사를 인물이 기억하거나 갈래 플래그가 켜지면 안 된다.
- 카드 대기·거절로 RNG, rolls, talks, 수치, 물건, 사건 시간, fate를 소비하지 않는다. `act`는 이 분기에서 이전 상태에 pending만 추가하거나 제거해 반환하며 settleFate를 실행하지 않는다. 62차 rewrite는 기존 전체 이전 상태 반환을 유지한다.
- 승인할 때 저장한 계획을 한 번만 실행한다. 모델에 다시 해석시키거나 같은 범위·bold를 두 번 확인하지 않는다. 이미 위험 경고를 받았다는 `warned`는 **범위 승인**이 아니며 scope 확인을 생략할 수 없다.
- 현재의 큰 행동 의도 확인을 별도로 유지한다면 같은 pending 형식을 쓰되, 명확한 일반 행동에 새 확인을 추가하지 않는다. 범위 확인 승인 후 기존 큰 행동 카드를 또 띄우지 않는다. 새로운 자유 입력 비트를 만들지 않는다.
- `ImprovMark.target/deed/bold`를 pendingLuck에도 그대로 넣는다. 행운으로 miss를 mixed로 바꿀 때 같은 목표를 사용한다. 확인·행운·저장 재개가 목표를 다시 고르는 지점이 되어서는 안 된다.
- 완료 기록은 기존 check에 improv를 붙인다. 성공한 check의 deed만 성취 기억으로 읽는다. miss, 미승인 pending, 실제 실행 전 입력 기록을 성공 기억으로 읽지 않는다. 별도의 영구 임의 플래그 목록은 만들지 않는다.

옛 저장은 새 선택 필드 없이도 읽는다. 새 판정을 시작할 때부터 새 계약을 적용한다. 단, **이미 굴렸는데 목표가 저장되지 않은 옛 pendingLuck**은 성공 계약을 복원했다고 간주할 수 없다. 그 예외는 저장 경계에서 명시한다. 기존 miss를 그대로 마무리하거나 그 판정 전 저장으로 돌아가는 선택을 제공하고, 목표를 추측한 mixed 업그레이드는 하지 않는다. 실제로 판정 전 저장이 없으면 되돌리기 단추를 제공하지 않는다. RNG를 몰래 되감거나 옛 입력을 새 성공으로 위조하지 않는다. 보통 저장의 후속 진행과 이 희귀한 미완료 옛 판정의 한계를 구분해 검증·보고한다.

## 엔진 적용 순서

1. **입력 경계**: 기존 `parseStoryInput`이 행동/말을 나눈다. 괄호 안 action만 기법·목표 해석에 사용하되, 함께 적은 발화는 따로 보존한다. 괄호 오류와 무괄호 행동 안내는 기존 62차 계약대로 처리한다.
2. **판정 계약 확정**: absurd/idle/odd는 기존 비판정 경로. 나머지는 목표와 비용 가능성을 판정 전에 확정한다. 목표/비용이 성립하지 않으면 scope 안내를 한다. 해석에 없던 목적을 장면 aim에서 채우지 않는다.
3. **improvRoll**: 현재 능력치·난도·risk·bold를 사용한다. goal을 적용하기 위해 target 접근법의 item/mods/before/said를 가져오지 않는다.
4. **improvSpec**: 일반/큰 즉흥의 반응·실패 규칙은 재사용한다. 목표 성공의 핵심은 `GoalSpec.effects/next`다. 일반 즉흥 결과에 있던 “칼을 거두지 않는다” 같은 고정 상황 단정은 완료 사건과 목표에 맞게 콘텐츠에서 제거한다. 런타임 출력 필터로 지우지 않는다.
5. **finishResolve**: crit/hit/mixed에는 같은 목표 성취를 합친다. 고정 접근법의 목표도 같은 함수에서 적용한다. 방법별 hit 보너스와 crit 보너스는 별도이며 목표 효과를 두 번 더하지 않는다. miss에는 목표 효과·성공 next·성공 deed를 적용하지 않는다.
6. **분기 확정**: 목표 효과를 반영한 상태에서 GoalSpec.next를 선택해 실제 비트 ID로 고정한다. 그 뒤 비용이 의심·관계 수치를 바꿔도 성공 경로를 원래 대본으로 다시 계산하지 않는다. 같은 판정의 비용이 탈주를 재포획으로 바꾸는 목표는 유효한 비용 계약이 아니다.
7. **연출과 효과**: 서술에는 확정한 deed·성취·독립 비용·도착 상태를 준다. 효과는 기존 엔진이 한 번 적용한다. 목표가 입력한 기법을 대신 서술하지 않도록 한다. `preempt`는 성공한 deed에만 호출하고 기존 대사 중복 방지로만 쓴다. 목표 달성·분기 보존의 증거로 사용하지 않는다.
8. **leaveOutcome**: 목표가 있으면 위에서 정한 next가 우선이다. local은 완료 사건을 기록한 뒤 기존 진행을 따른다. local을 처리하려고 턴을 초기화하거나 같은 질문을 다시 걸지 않는다. 다음 대본이 성취와 양립하지 않는 입력은 2단계에서 local로 접수할 수 없다.

새 목표는 flags/route/소지품 등의 실제 효과로 후속 상태를 보존한다. “이미 도주했음”이라는 글만 prompt에 추가하고 `leaveOutcome`은 기존대로 두는 해법은 채택하지 않는다.

## 대가 계약

`PriceSpec`에 임의 의미 태그나 금지 낱말 필드를 더하지 않는다. 기존 `if`, `effects`, `once`, `spoken`과 명시 ID 목록을 사용한다.

`priceCandidates`의 순서는 반드시 다음과 같다.

1. goal이 있으면 `goal.price`, 없으면 기존 `outcome.price`로 허용 목록을 확정한다. 목록 미지정은 기존 비트 표, 빈 목록은 **추첨 없음**이다.
2. weight, if, once, spoken 조건을 적용한다.
3. 그 후보 **안에서만** 사용한 소지품의 비용을 우선한다.
4. 기존 used/fresh와 시드 선택을 적용한다.

새 목표의 mixed에는 실제 비용이 있어야 한다. 인라인 비용을 유지하는 기존 결과는 별도 추첨이 없어도 유효하다. 명시 비용도 없고 후보도 없는 새 목표를 mixed로 접수하지 않는다. 조건 때문에 비용 후보가 전부 사라지거나 자원 바닥에서 차감이 0이면 “비용을 냈다”고 간주하지 않는다. 판정 전에 다른 유효한 독립 비용을 선택할 수 있는지 확인하고, 없으면 현재 가능한 판정 범위를 설명한다. 성공을 굴린 뒤 임의 비용을 만들어 내지 않는다.

목표별 비용 목록과 if는 저자가 검증한다. 도주 뒤 칼 재밀착·퇴로 차단, 물 확보 뒤 그 물 전부 상실, 설명 성공 뒤 전달 실패는 제외한다. mental -1도 정신력이 이미 0이면 실효 비용이 아니다. 체력·의심·귀찌 비용은 임계치, onEnter 비용, fates까지 포함해 성공을 취소하지 않는 조건에서만 허용한다.

`settleFate`에 “이번 판이 성공이면 무시” 같은 사후 면제를 추가하지 않는다. 가격표와 목적지의 진입 효과가 잘못됐다면 그 소유자인 데이터/조건을 고친다. 성공 도주 뒤 경로가 재포획으로 이어지는 경우도 경로 자체를 고친다. 임계치 검증은 새 목표를 접수할 수 있다는 사전 계약의 시험이다.

`scenario.ts`는 목표 ID/참조, next 존재, 조건 문법, price ID/soft 조건, 목표 효과와 성공 outcomes의 중복·충돌을 검사한다. 이야기 문장까지 구조 검사로 보장할 수 없으므로 비용 문장·후속 대사는 스토리 QA에서 읽어야 한다.

## GM 생성 계약

`prompt.ts`의 “장면 목표로 끌고 온다”, 일괄 제압/무장 해제 성공 금지, “대가는 행동이 어긋나는 모습”을 제거하고 다음 우선순위로 맞춘다. 수정은 문법 담당자와 리드가 해당 파일 소유권을 정리한 뒤 한다.

1. 이번 판정 전에 확정한 플레이어 목표와 결과 등급.
2. 코드가 적용할 성공 상태와 독립 비용.
3. 원작 인물의 성격·말투와 실제 현재 상태.
4. 위 세 조건과 양립하는 장면 전개.

crit/hit/mixed의 deed는 실제 성취다. miss의 deed는 시도한 목표이며 완료로 읽지 않는다. 목표 범위를 승인해 바꾼 경우에는 원래 raw text의 더 큰 목표보다 **승인한 계획**이 기준이다. 혼합 입력의 바깥 말은 원래 말 그대로 보존한다.

`narrateFallback`도 같은 판정 계약으로 구성한다. 성공이면 판정 전에 검증한 deed와 목표 성취를 명시하고 독립 비용을 덧붙인다. 실패라면 시도·실패를 서술한다. 성공 deed가 unsafe라서 판정 후 사라지는 상황을 만들지 않도록 해당 검증을 해석/계획 경계로 옮긴다. 실패한 생성 때문에 무관한 neutral 줄로 성공 목표를 지우지 않는다.

기존 check의 성공 deed를 현재 판의 성취 기록으로 `buildSystem`에 전달한다. heard는 플레이어가 입력한 말·시도, check의 성공 deed는 실제 이뤄진 사건으로 구별한다. 기록에 없다면 과거 성공을 지어내지 않는다. 이 기록은 현장 사건을 기억하기 위한 것이고 물건 소유·지속 부상·거리 같은 엔진 상태를 대신하지 않는다.

일반 진행 중 GM의 설명·선택지 낭독·훈수는 추가하지 않는다. 직접 재입력 안내와 필요한 사전 범위 조정만 규칙 카드 또는 짧은 안내로 낸다. absurd는 기존대로 인물이 세계 안의 반응으로 받는다.

위험·난도와 불가능은 구별한다. 강한 적의 저항은 어려운 판정의 이유가 될 수 있다. 능력·거리·장비상 성립하지 않는 성공을 약속하거나, 원작 대본을 지키기 위해 성공을 취소해서는 안 된다. 입력이 여러 목적을 포함하면 하나로 연결되는 전체 목적을 보존하고, 독립 목적을 한 판정으로 처리할 수 없을 때만 굴리기 전 범위를 묻는다.

기존 confirm 이벤트가 text/yes/no를 지원하므로 정상 새 판정의 웹 변경은 필요하지 않다. 옛 미완료 판정 호환 안내는 기존 저장 오류/안내 표면을 재사용하고, 실제로 없는 복원 동작을 UI에 약속하지 않는다.

## 불변식과 필요한 검증

이 문서는 시험을 실행한 결과가 아니다. 아래는 구현 완료 전에 충족할 시험 계약이다.

| 경계 | 반드시 깨뜨려 볼 회귀 | 관측할 증거 |
|---|---|---|
| Engine.act | 같은 도주 목표에 기존 단추/새 기법, hit/mixed/crit | 같은 도주 플래그·성공 경로. 실제 방문 비트 로그에 b03_ask/b06 강제 복귀·재포획 없음 |
| Engine.act | 같은 즉흥 기법의 miss와 행운→mixed | miss는 목표 미적용. 업그레이드는 같은 target/deed로 성취·비용 각각 한 번 |
| Engine.act | scope 카드 생성/거절/다른 입력/저장 재개/승인 | 미승인에는 pending 외 게임 상태 불변. 승인 한 번에 판정 한 번. stat/difficulty/bold/target 유지 |
| Engine.act | attack 경고가 있는 불가능·미지원 목표 | warned여도 scope를 생략하지 않음. 성공 주사위 뒤 목표 축소 없음 |
| Engine.act | 관련 없는 입 맞춤·단순 모래 뿌리기 | 실제 완료 사건과 큰 반응. 자동 도주·물건 생성·사랑 강요 없음. 후속 생성에도 성공 기록 전달 |
| Engine.act | 지속 무장 해제/구속 해제/먼 거리 접촉 | local로 접수하지 않음. 허용한 goal의 상태와 전체 후속 경로 확인, 아니면 사전 선택 |
| 해석 경계 | 없는 target, ready+none, 빈/위험한 deed, LLM 장애 | 무목표 improv를 대신 굴리지 않음. rewrite 무소비 |
| 62차 입력 | ASCII/전각 괄호, 혼합 발화, 여러 목적, 잘못된 괄호 | 행동/말 분리 보존. 축소한 목적을 raw text가 다시 덮지 않음 |
| 비판정 | absurd/odd/idle와 위험 단어가 섞인 현대 도구 | 주사위/목표 효과/성공 기억 없음. 기존 talks/worldMove 계약은 별도 관측 |
| prices 단위 | 명시 allowlist 밖 소지품 비용, `price: []` | 선호 소지품도 목록 밖이면 0개. 빈 목록은 추첨 0개 |
| prices/Engine | 정신력 0/1, 체력 0/1, 귀찌·의심 임계치, 이미 손상한 물품 | 실효 비용과 성취 모두 유지. 비용이 0이 되거나 성공 뒤 fate로 취소되는 조합은 판정 계약에 접수되지 않음 |
| 생성/fallback | 성공한 뒤 생성 실패, miss에서 생성 실패 | 성공 deed가 사라지지 않고 miss를 완료로 쓰지 않음. 양쪽 모두 문법·성격·독립 비용 확인 |
| 저장 | 새 pendingIntent/pendingLuck와 기존 일반 저장 | 복원 후 의미·RNG·비용 중복 없음. 목표 없는 옛 pendingLuck 예외는 명시적으로 구분 |
| 전체 경로 | 8개 free 비트의 목표별 hit/mixed, 이후 결말/후속 화까지 | 목표 효과만 확인하고 끝내지 않고 실제 모든 대사·CG·물건·상태를 읽음 |

모델 없이 하는 시험은 상태·경로·판정·비용의 구현 계약을 보호한다. 해석기가 새 기법을 같은 목표로 읽는지, local과 지속 목표를 나누는지, 실제 생성이 성취를 부정하지 않는지는 **문서에 없는 표현을 포함한 실제 GM 실행**으로 별도 확인한다. 같은 단어를 넣은 모의 해석 시험으로 실제 의미 해석이 검증됐다고 보고하지 않는다.

## 채택하지 않는 축소안

- `targetApproach` 하나를 붙여 접근법 전체를 복사: before/item/said/mods와 기법별 문장까지 잘못 실행한다.
- 자유 텍스트 goal만 prompt에 추가: 엔진 효과와 다음 경로가 여전히 없으므로 성공 서술 뒤 원래 대본으로 복귀한다.
- 모든 즉흥을 가장 비슷한 접근법에 연결: 입 맞추기를 미인계로, 모래 뿌리기를 도주로 바꾸며 하지 않은 목적을 강제한다.
- 목표 없는 경우 local로 처리: 지속 무장 해제·탈출을 말로만 성공시킨다.
- 성공 후 실패 표현 검사/낱말표 확장/재포획 면제: 입력·상태·분기 계약의 누락을 고치지 않는다.
- 목표마다 별도 해석·판정·저장 엔진 추가: 기존 resolve/confirm/luck/price 경계를 공유하면 필요 없다.

설계상 남기는 가정은 두 가지다. 첫째, 현재 제품은 작가가 정한 경로를 가진 VN형 솔로 TRPG여서 임의의 지속 세계 상태를 모두 생성하지 않는다. 둘째, 가능한 목표라도 구현된 후속 상태가 없는 경우에는 그 한계를 판정 전에 밝히는 선택을 허용한다. 이 가정을 받아들이지 않고 모든 지속 목표를 즉시 허용하려면 작은 즉흥 필드 패치가 아닌 세계 상태와 후속 장면 생성 설계가 필요하다.
